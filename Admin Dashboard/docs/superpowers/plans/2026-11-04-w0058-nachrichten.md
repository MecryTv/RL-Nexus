# Nachrichten über den Bot (W-0058) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Seite Datenschutz → Nachrichten im Admin Dashboard: DMs über den Bot als Bild im Stil I1 an eine Person oder an alle mit Daten, mit Vorlagen, Vorschau, Test, Hintergrundversand und Verlauf (Entwurf R1, Variante N-A).

**Architecture:** Inhalt und Regeln liegen in `shared/messages.ts` (Server und Oberfläche). Das Admin Dashboard zeichnet das Bild selbst mit `@napi-rs/canvas` wie die Sperr-DM und schickt es über `postDirectMessage`. Versand an alle läuft über eine Uhr alle 2 s mit dem Stand in MariaDB (`bot_messages`, `bot_message_recipients`), Vorlagen in `bot_message_templates`. Personen-Spalten hängen an den Nutzerdaten von W-0051, damit Auskunft und Löschung sie kennen.

**Tech Stack:** Node 24 strip-only TS, Fastify, MariaDB, `@napi-rs/canvas`, React 19, SCSS-Module. Keine neuen Pakete.

**Spec:** `Admin Dashboard/docs/superpowers/specs/2026-11-04-nachrichten-ueber-den-bot-design.md`

## Global Constraints

- Strip-only TypeScript: keine enums, keine Parameter-Properties, keine Namespaces.
- Farben: blau #5aa9e6, gold #f0b232, gruen #23a55a, lila #a46cf0, rot #f23f43, grau #80848e.
- Grenzen: Stempel 1–14, Titel 1–80, Einleitung bis 160, große Zeile 1–40 mit Notiz bis 160, bis 3 Kacheln (Überschrift bis 30, Text 1–600), bis 2 Knöpfe (Beschriftung 1–40).
- Platzhalter nur `{name}` und `{datum}`; Datum „4. November 2026“, Europe/Berlin.
- Eine DM alle 2 Sekunden (`SEND_EVERY_MS = 2000`). Anhalten bei einem `spam`-Fehler sofort, bei 5 `trouble` hintereinander.
- Rechte: an eine Person, Test, Vorschau, Vorlagen: Admin und Developer. An alle, Anhalten, Weiter, Abbrechen: nur Developer (`developerOnly`).
- Aufbewahrung: Nachricht an eine Person 90 Tage ganz; Empfänger einer Nachricht an alle 90 Tage nach `finished_at`; Nachricht an alle 3 Jahre.
- Sätze an die Oberfläche genau wie in der Spec, Teil 1 und Teil 4.
- Texte auf Deutsch im Stil des Dashboards. Keine `.env` lesen. Commits ohne Co-Authored-By, nur gezielt Dateien stagen. Kein VPS ohne Anweisung des Nutzers. Beim Prüfen im Browser keine echte DM verschicken.

## Review Focus

1. Neustart oder Absturz zwischen „Discord hat angenommen“ und dem Update: niemand bekommt die DM zweimal (Zeile `sending` → `failed` beim Start). Test in Task 4.
2. Die Person wird mitten im Lauf gelöscht (W-0051 entfernt ihre Empfängerzeile): die Runde läuft weiter und endet mit `done`, Zahlen stimmen. Test in Task 4.
3. Ein Name mit `{datum}`, `$&` oder `$1`: steht so im Bild, wird nicht ersetzt. Test in Task 1.
4. Drei Kacheln mit je 600 Zeichen und Zeilenumbrüchen: Bild wächst, nichts abgeschnitten, Alt-Text höchstens 1024. Test in Task 2.
5. Admin ruft `POST /api/messages/all`, `/pause`, `/resume`, `/cancel` direkt auf: 403. Test in Task 5.

## Rulings gegenüber der Spec

- `checkContent` heißt `checkMessage`: `server/checks/content.check.ts` exportiert schon `checkContent`.
- Platzhalter sind in allen Textfeldern erlaubt, nicht nur in Titel, Einleitung, großer Zeile und Kacheln (weniger Sonderfälle; URLs bleiben ohne).
- Datenschutzerklärung: ein eigener kurzer Abschnitt statt eines Satzes im Abschnitt zum Bot, weil es dort keinen passenden Abschnitt gibt und Speicherdauer und Rechtsgrundlage dazugehören.
- „Löschung beantragt“ heißt `geplant`, `angehalten` oder `geloescht`; `abgebrochen` (etwa „Das war ich nicht“) zählt nicht.
